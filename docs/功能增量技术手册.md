## 1. BM25 双路召回 + RRF 混合检索

### 1.1 背景

原有检索只有一路：**向量语义搜索（Chroma cosine similarity）**。它的问题在于"只懂语义、不懂关键词"——"买卖100张身份证"这个 query 的向量距离离刑法280条第3款太远（`>0.42`），被 `MAX_DISTANCE` 阈值过滤掉了，导致AI助手答不上来。

### 1.2 做了什么

**新建 `app/services/bm25_service.py`**（约 130 行）：

```
BM25 内存索引（Lazy Load）
├── 法条索引：从 MySQL law 表加载全部条文，拼接《法名》+章+条号+正文
└── 案例索引：从 MySQL case_ref 表加载全部案例，拼接标题+四段正文
```

**修改 `app/services/retrieval_service.py`**（约 +30 行）：

```
用户提问
  ├─→ ✦ 向量检索（Chroma cosine）→ 语义相似
  └─→ ✦ BM25 检索（jieba分词）→ 关键词匹配
       └─→ RRF 融合 → 合并排序 → top_k
```

### 1.3 关键技术点

| 技术 | 用途 | 说明 |
|------|------|------|
| BM25Okapi | 全文检索算法 | `rank_bm25` 库，基于词频(TF) + 逆文档频率(IDF)打分 |
| jieba 分词 | 中文分词 tokenizer | 对中文法律文本做词语级切割，BM25 需 tokenized corpus |
| RRF | 多路结果融合 | Reciprocal Rank Fusion：`score(d) = Σ 1/(k + rank)`，k=60 |
| Lazy Load | 首次查询时加载索引 | 避免启动时全量加载拖慢 app 启动 |

**RRF 融合公式**：

```
RRF(d) = 1/(60 + rank_vector(d)) + 1/(60 + rank_bm25(d))
```

如果某路没召回该文档，该路的 rank 视为无穷大，贡献为 0。

### 1.4 文件改动

| 文件 | 操作 | 说明 |
|------|------|------|
| `app/services/bm25_service.py` | **新建** | BM25 索引构建 + 搜索，lazy load |
| `app/services/retrieval_service.py` | **修改** | 双路召回 + RRF 融合 |

## 2. MCP Server（明镜协议接入）

### 2.1 背景

MCP（Model Context Protocol）是 Anthropic 推动的开放协议，让 LLM 客户端（Claude Code、Claude Desktop、Cursor 等）能发现并调用外部工具的标准化方式。把明镜系统的数据能力包成 MCP Tool，任何人可以在任意 MCP 客户端中直接查询案例、法条和统计。

### 2.2 做了什么

**新建 `app/mcp_server.py`**（约 220 行）：

```
MCPServer("明镜·要素式智能受理系统")
│
├── search_law(query)      → 语义搜索法条（走 retrieve）
├── search_case(query)     → 语义搜索案例（走 retrieve）
├── get_case(case_id)      → 精确查案例详情（MySQL）
├── get_law(law_id)        → 精确查法条详情（MySQL）
├── get_stats()            → 知识库统计信息（MySQL）
└── search_case_by_title(keyword) → 按标题模糊搜索（MySQL）
```

**配置 `.claude/settings.local.json`**：

```json
{
  "mcpServers": {
    "mingjing": {
      "command": "python",
      "args": ["-m", "app.mcp_server"],
      "cwd": "C:\\Code\\Project\\ai-qiuzhao\\mingjing-intake",
      "env": { "PYTHONIOENCODING": "utf-8" }
    }
  }
}
```

### 2.3 关键技术点

| 技术 | 用途 | 说明 |
|------|------|------|
| MCPServer (v2) | MCP 协议服务端 | `from mcp.server.mcpserver import MCPServer` |
| stdio transport | 进程间通信 | MCP 通过 stdin/stdout 传输 JSON-RPC，无需 HTTP |
| `add_tool` 装饰器 | 注册工具函数 | `@server.add_tool` 自动提取函数签名 → JSON Schema |
| JSON-RPC | MCP 协议基础 | 请求/响应格式：`{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{}}` |

**Claude Code MCP 集成流程图**：

```
Claude Code
  │  读取 .claude/settings.local.json
  │  ┌─ mcpServers.mingjing.command = "python -m app.mcp_server"
  │  │
  │  ↓ 启动子进程（stdio）
  └──→ MCPServer 进程
        │  初始化握手（initialize）
        │  注册 tools（tools/list）
        │
        │  用户提问 → LLM 决定调哪个 tool
        │  tools/call → 执行 → 返回结果
        │  LLM 用结果回答
```

| 文件 | 操作 | 说明 |
|------|------|------|
| `app/mcp_server.py` | **新建** | MCPServer + 6 个工具 |
| `.claude/settings.local.json` | **新建** | MCP 配置入口 |
| `requirements.txt` | **修改** | 加 `mcp>=2.0` |

## 3. AI 助手 Function Calling 操作 DB

### 3.1 背景

原 AI 助手只有一条路：**RAG 检索 → LLM 回答**。当 RAG 检索不到时，系统只回复"知识库暂无依据"——"查一下张三的案子"这种明显能通过 SQL 回答的问题也答不上来。

### 3.2 做了什么

**修改 `app/llm/provider.py`**（`chat()` 支持 tools 参数）：

```python
def chat(self, messages, temperature=0.3, tools=None):
    # 不传 tools → 原行为不变
    # 传 tools → llm.bind_tools(tools) → 返回含 tool_calls 的 AIMessage
```

**修改 `app/api/assist.py`**（新增 ~90 行）：

```
用户提问
  ↓
RAG 检索
  ↓
  ├─ 有命中 → LLM 流式回答（原流程）
  │
  └─ 无命中 → 判断是否像 DB 查询？
      ├─ 是 → LLM 非流式调用 + tools
      │   ├─ 调工具 → 执行 SQL → 结果注入 prompt → LLM 流式回答
      │   └─ 不调工具 → 原兜底回复
      │
      └─ 否 → 原兜底回复（问候/时间/NOHIT）
```

### 3.3 关键技术点

| 技术 | 用途 | 说明 |
|------|------|------|
| OpenAI Tool Calling | LLM 驱动工具调用 | 通过 `bind_tools()` 将 DB 工具描述注入 LLM |
| LLM 自主决策 | 不硬编码正则 | LLM 决定何时调哪个工具（正则只做路由触发） |
| 两阶段调用 | 非流式+流式组合 | 第一阶段非流式（带 tools）→ 可能返回 tool_call；第二阶段流式（注入 tool 结果）→ 逐 token 推送给前端 |
| 保底设计 | RAG 无命中才进 FC | 有 RAG 命中时走原流程，不增加延迟 |

**Function Calling 的 JSON Schema 定义**：

```python
DB_TOOLS = [
    {
        "type": "function",
        "function": {
            "name": "search_cases",
            "description": "按案由、案号、当事人名等关键词搜索案例库",
            "parameters": {
                "type": "object",
                "properties": {
                    "keyword": {"type": "string", "description": "搜索关键词"}
                },
                "required": ["keyword"],
            },
        },
    },
    # ... 类似定义 get_case_detail, search_laws, get_kb_stats
]
```

**执行流程时序**：

```
用户: "搜一下买卖身份证的案例"
  │
  ├── 1. RAG 检索 → 无命中
  ├── 2. 正则路由 → _DB_QUERY_PATTERN 匹配 ✅
  ├── 3. LLM 非流式调用（绑定了 tools）
  │      ↓ (300ms)
  │     LLM 返回: tool_call(name="search_cases", args={"keyword": "买卖身份证"})
  │
  ├── 4. 执行 DB 工具 → 返回 3 条案例
  ├── 5. 注入 tool 结果到 prompt
  ├── 6. LLM 流式调用 → 逐 token 推送给前端
  │      ↓ (1~3s)
  │     "根据数据库查询，找到以下涉及买卖身份证的案例：1...2...3..."
  │
  └── 7. 保存会话历史 → 完成
```

### 3.4 文件改动

| 文件 | 操作 | 说明 |
|------|------|------|
| `app/llm/provider.py` | **修改** | `chat()` 新增 `tools` 参数 |

## 4. 涉及知识点汇总

### 4.1 检索相关

| 概念 | 说明 |
|------|------|
| **BM25** | 基于词频和逆文档频率的排序函数，全文检索的基石算法。`rank_bm25` 库实现了 Okapi BM25 变体。 |
| **RRF (Reciprocal Rank Fusion)** | 最简单的多路融合方法：不依赖分数标准化，只依赖排序位置。k=60 是业界经验值。 |
| **Embedding** | 将文本映射到高维向量空间。text-embedding-v3 输出 1024 维向量。Cosine 距离衡量语义相似度。 |
| **HNSW** | Hierarchical Navigable Small World，Chroma 底层使用的近似最近邻搜索算法。 |
| **jieba 分词** | 中文分词库。内置词典 + HMM 模型，支持自定义词典。法律文本中准确率较好。 |

### 4.2 MCP 协议相关

| 概念 | 说明 |
|------|------|
| **MCP** | Model Context Protocol，Anthropic 推动的 LLM-工具集成标准。类比"AI 界的 USB-C"。 |
| **传输方式** | `stdio`（进程间 stdin/stdout）和 `sse`（HTTP Server-Sent Events）两种。stdio 适合 Claude Code 等本地客户端。 |
| **JSON-RPC 2.0** | MCP 底层协议。`initialize` → `tools/list` → `tools/call` 三阶段握手。 |
| **Tool Schema** | 工具的 JSON Schema 描述。参数类型支持 `string`/`integer`/`number`/`boolean`/`object`/`array`。 |

### 4.3 Function Calling 相关

| 概念 | 说明 |
|------|------|
| **Tool Calling** | OpenAI 定义的标准：LLM 返回结构化 tool_call，服务端执行后回传结果。`ChatOpenAI.bind_tools()` 自动将 Python 函数/JSON Schema 转为 LLM 可识别的工具描述。 |
| **AIMessage.tool_calls** | LangChain 中 LLM 返回的工具调用标识。包含 `name`（工具名）、`args`（参数字典）、`id`（调用 ID）。 |
| **非流式 + 流式组合** | 一种优化策略：第一阶段非流式调用（判断是否调工具），第二阶段流式调用（推送到前端）。避免流式过程中执行工具的复杂状态管理。 |
| **SSE (Server-Sent Events)** | FastAPI 中实现流式对话的标准方式。`StreamingResponse` 包装生成器，每个 token 作为一个 `event:delta` 推送。 |

### 4.4 工程实践

| 实践 | 说明 |
|------|------|
| **Lazy Load** | BM25 索引在首次查询时构建，而非服务启动时。避免冷启动延迟，但也带来第一次查询慢的问题（~几秒）。 |
| **幂等设计** | Chroma upsert 按主键覆盖；MySQL `ON DUPLICATE KEY UPDATE`。重跑不会产生重复数据。 |
| **熔断与冷却** | Provider 云端 API 失败后冷却 60s 再重试，不永久降级。防止短暂抖动导致整个进程降级。 |
| **`vector_synced` 状态机** | 0=待处理，1=已完成，2=无法向量化（跳过）。支持中断续跑。 |

## 5. 坑与解决方案

### 5.1 BM25 假阳性：医疗机构匹配"100张"

**现象**："买卖100张身份证"查询的 BM25 结果中出现了医疗机构管理条例（"床位不满100张"），BM25 分数 22.316。

**原因**：jieba 分词将"100"+"张"作为独立 token。医疗机构管理条例第22条包含"床位不满100张"，BM25 认为关键词匹配度高。

**解决方案**：不需要特殊处理。BM25 假阳性条目在 RRF 融合后会被排名靠后的向量结果压制。如果假阳性排到前面，说明该查询确实缺少强匹配的向量结果，而 BM25 的"沾边匹配"也聊胜于无。

**教训**：BM25 适合召回（recall），不适合排序（precision）。**RRF 融合就是来解决这个问题的。**

### 5.2 MCP v2 API 变化：FastMCP → MCPServer

**现象**：`from mcp.server.fastmcp import FastMCP` → `ModuleNotFoundError: No module named 'mcp.server.fastmcp'`

**原因**：安装了 `mcp>=2.0`，但 v1 的 `FastMCP` 在 v2 中更名为 `MCPServer`。

**解决方案**：
```python
# v1（mcp<2）
from mcp.server.fastmcp import FastMCP
mcp = FastMCP("name")
@mcp.tool()  # 装饰器
def my_tool(): ...

# v2（mcp>=2.0）
from mcp.server.mcpserver import MCPServer
mcp = MCPServer("name")
@mcp.add_tool  # 注意不是 @mcp.add_tool()
def my_tool(): ...
```

**教训**：检查版本号。查看最新 API 用 `pip show mcp`，或查看官方迁移指南。

### 5.3 MCPServer.instructions 只读属性

**现象**：`server.instructions = "..."` → `AttributeError: property 'instructions' has no setter`

**原因**：MCPServer 的 `instructions` 是构造函数参数（`__init__`），不是可写属性。

**解决方案**：创建时传入：
```python
server = MCPServer("name", instructions="xxx")
```

**教训**：对于新引入的库，先检查构造函数签名（`inspect.signature(MCPServer.__init__)`）再写属性赋值。

### 5.4 Windows 中文编码：GBK 炸 stdout

**现象**：MCP Server 运行后无输出，工具调用无响应。测试发现 Python 输出的 "📊"、"🟦" 等中文/emoji 字符在 Windows 控制台 GBK 编码下报错。

**原因**：Windows 终端默认编码 GBK（cp936），而 MCP stdio 传输中返回的中文字符串包含 UTF-8 编码的字符，导致 `print()` 时 `UnicodeEncodeError`。

**解决方案**（双重保险）：
1. 在 `mcp_server.py` 开头强制 stdout 用 UTF-8：
   ```python
   if sys.platform == "win32" and hasattr(sys.stdout, "reconfigure"):
       sys.stdout.reconfigure(encoding="utf-8")
   ```
2. 在 `.claude/settings.local.json` 中设置环境变量：
   ```json
   { "env": { "PYTHONIOENCODING": "utf-8" } }
   ```

**教训**：在任何涉及中文输出的 Windows 服务/子进程中，**必须显式设置 UTF-8 编码**。不要在输出中使用 emoji。

### 5.5 MCP 管道测试限制：stdio 单消息阻塞

**现象**：通过 `echo {json} | python -m app.mcp_server` 方式测试 MCP Server，只能收到 initialize 响应，收不到 tools/call 响应。

**原因**：stdio 传输的 MCP Server 读取 stdin 的一行 JSON，处理，回复一行 JSON，然后继续读下一行。通过管道一次传入多行 JSON 时，Server 逐行处理，但管道的 stdout 可能被缓冲，或者 Server 处理完第一行后 stdin 已关闭导致进程退出。

**解决方案**：用 Python `subprocess` 或 heredoc 方式发送多条消息。真实客户端（Claude Code）通过子进程交互式通信，不存在此问题。开发阶段可通过直接内省（`server._tools`）或 `call_tool()` 进行单元测试。

### 5.6 刑法280条第3款不在向量检索结果中

**现象**：查询"买卖100张身份证"时，刑法280条（含第3款买卖身份证件罪）不在向量检索结果中，反而是280条之一（使用虚假身份证件罪）被召回。

**原因**：刑法280条原文包含3款内容（伪公文印章罪、伪公司印章罪、买卖身份证件罪），三款混合在同一文档中。Query embedding 与 280条全文的 cosine distance 超过了 `MAX_DISTANCE=0.42`阈值，被过滤掉了。而280条之一（使用虚假身份证件）篇幅较短、语义更集中，反而更接近 query。

**解决方案**：这不是向量检索的问题，而是**法律条文存储粒度的问题**。一条法律包含多款时，作为一个文档 embedding 会稀释语义。理想方案是"一款一条"（按款拆分），但这是数据清洗层面的改动。**BM25 混合检索恰好绕过这个问题**——BM25 看到"买卖"+"身份证"关键词就匹配。

**教训**：向量检索对"多条混合的文档"效果差。如果某个场景频繁出现此类问题，应考虑调整知识库切分策略（按款切条而非按条切）。

### 5.7 法条数据量暴增（59K条）导致 BM25 加载慢

**现象**：第一次 BM25 查询耗时 5~15 秒。

**原因**：`law` 表中有 59443 条记录（这是多个法律版本导致的，比如同一法律的"修正前""修正后"不同版本都存在于库中）。jieba 对 5 万+ 法律条文逐条分词构建 BM25 索引，加上 jieba 自身的词典加载，总耗时较大。

**解决方案**：Lazy Load 机制——只在首次查询时加载，之后的查询直接命中内存索引。如果冷启动延迟不可接受，可以在服务启动时异步预加载（但实际影响不大，因为 AI 助手会话持续数分钟，一次冷启动后可服务数十次查询）。

**潜在优化**：`law` 表的 59K 条数据存在**大量重复**（同一法律的不同层级都有完整的300+条条文）。这降低了 BM25 效率。清理重复的法律版本可以将数量降到 ~5K 条，BM25 索引速度提升 10 倍。**这不是本次改动的范围**，但值得注意。

### 5.8 Chroma query API 参数名：`where` vs `where_filter`

**现象**：`collection.query(where_filter={"chunk_type": "child"})` → 参数不识别（静默忽略，导致结果为空）。

**原因**：Chroma 的 `query()` 方法接收的是 `where` 参数，不是 `where_filter`。这是编写时的笔误。

**解决方案**：
```python
# 错误
r = cases_col.query(query_embeddings=[qv], n_results=top_cases * 3,
                    where_filter={"chunk_type": "child"})

# 正确
r = cases_col.query(query_embeddings=[qv], n_results=top_cases * 3,
                    where={"chunk_type": "child"})
```

**教训**：使用不熟悉的库时，**写完代码后做一次完整的功能测试**。Chroma 的错误参数不会报错——只是静默忽略，导致"看起来跑通了但结果不对"。这就是为什么你看到 RAG 检索不返回案例的原因之一（另一个是 `vector_synced=0`）。
