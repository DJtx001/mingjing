## ⚠️ 暂缓（不是不做，是时机未到）

### 2. Rerank（Cross-encoder 重排）

**它解决什么**
- 从向量 + BM25 召回的结果中，用更重的模型重新排序
- 把最相关的前 3~5 条排到最前面

**为什么暂缓**
| 对比 | 双路 + RRF | + Rerank |
|------|-----------|----------|
| 额外召回 | BM25 补上关键词匹配 | 不召回新文档 |
| 排序精度 | RRF 够用 | 更细，但收益递减 |
| 推理成本 | 0 | 每次查询多 2~5 秒 |
| 模型部署 | 0 | 需 1~3 GB 模型文件 |

**最关键的问题**：如果 BM25 双路已经捞回了正确文档，Rerank 只是把排名从第 5 挪到第 1——**对 LLM 的回答质量几乎没有影响**，因为 top_k=4 的时候前 8 个候选里本来就包含了正确答案。Rerank 的收益在召回量（千/万级）时才显著，你目前的是**候选池本身就不大**。

**什么时候值得做**
- 用户反馈"AI 引用的法条/案例不对"，且 BM25 混合后仍没改善
- 明确是排序问题（正确文档在召回候选中，但排到了后面导致 LLM 没用）

### 3. LangGraph Plan-and-Execute

> **后续讨论补充**：用户提出用 LangGraph 做"AI 操作 DB"（查询案件、查统计等），
> 下面是 Plan-and-Execute 和直接 Function Calling 的方案对比。

**它解决什么**
- 将单次 RAG 查询扩展为"规划 → 多步执行 → 综合"的多跳流程
- 比如"被撞了对方全责没买保险要准备什么"→ 拆成 3 个子查询分别检索

**为什么暂缓**
1. **当前瓶颈不在这里**。买卖身份证没命中是检索召回的问题，不是编排的问题。把检索修好，单跳质量就在线了。
2. **2C4G 拖不动链式推理**。LangGraph 每多一跳就是一次 LLM 调用 + 检索，延迟成倍增长。
3. **LanfGraph 的真正价值在"需要外挂工具"的场景**（查日历、调 API、操作 DB），纯检索链用不上。它本质上是一套路由器，而你现在的系统只有一个目的地（RAG）。

#### 针对"AI 操作 DB"的场景：LangGraph vs Direct Function Calling

| 对比维度 | LangGraph Plan-and-Execute | 直接 Function Calling |
|----------|---------------------------|---------------------|
| **思路** | 用图定义"意图分类→工具选择→执行→汇总"的状态机 | 在现有 assistant 里注册工具函数，LLM 自主选择调哪个 |
| **代码量** | ~200 行（定义 Graph、节点、边、状态类型） | ~60 行（写工具函数、注册 tools list） |
| **新增依赖** | `langgraph` | 0（langchain 已有 tool calling 支持） |
| **对现有架构的影响** | 需要单独起一个 Graph 流程，assistant 逻辑重写 | 在 `app/api/assist.py` 中加 tools，已有 provider 直接支持 |
| **复杂查询** | 天然支持多步编排（先查案号再查进度） | 一次调用只调一个工具，多步需要 LLM 自行多轮 |
| **简单查询** | "查张三的案子"也要走 Graph 节点流转 | 一个 tool call 返回结果，更快 |
| **可调试性** | 每个节点可打断、可观察、可恢复 | 就是函数调用 + LLM 多轮，更黑盒 |
| **运维成本** | 图状态需序列化存 DB（长对话场景） | 无额外状态 |

**结论：在"AI 操作 DB"这个具体场景上，Function Calling 胜出。**

原因很简单：你 95% 的 DB 查询都是**单条 SQL 就能回答的问题**（查案号、查进度、搜法条、统计数量）。不需要"规划→拆分→多步→综合"——LLM 看一眼 query，选一个工具，执行，完事。

LangGraph 的真正价值在需要**动态多步编排**的场景（先 A 查询，结果决定 B 或 C 分支，然后 D 汇总），你的"操作 DB"目前不需要这个复杂度。

**什么时候 LangGraph 值得做**：当出现"单次 Function Calling 搞不定"的流程时——比如用户问"对比张三和李四的案子，谁的调解金额更高"（查两个案子 → 对比 → 汇总），这时再上 LangGraph 做编排。目前先 Function Calling，够用。

**什么时候值得做**
- 出现用户明确需要的、**单次检索无法回答**的问题类型（如跨案件比对、时效性计算、多步逻辑推理）
- 并且 BM25 混合 + 评测验证后，确认问题是"需要多步"而非"检索不准"
- 并且 Function Calling 单工具模式已上线，发现确实需要多步编排

## ❌ 暂不投入（代价大于收益）

### 4. Neo4j 案例图谱

**它解决什么**
- 把案例中的实体（当事人、案由、法院、争议焦点、调解方案）抽取出来建成图
- 支持"找相似案子的调解方案"这类图查询
- 可视化展示关系

**为什么现在不推荐**

| 成本项 | 评估 |
|--------|------|
| Neo4j 容器 | 加 1 个容器，云端 2C4G 内存吃紧 |
| 实体抽取 | LLM 抽精度可以但耗 token，规则抽覆盖率低 |
| 数据迁移 | 已有 5000+ 案例全部重跑抽取 |
| 维护成本 | 新增案例也要跑抽取 pipeline，否则图慢慢过时 |
| 前端展示 | 需要一个新的"关系浏览"页面 |
| **收益** | 当前**没有任何一个用户场景依赖图查询** |

**最关键的问题**：你现在的**搜索是"关键词/语义"模式**，"找相似案子"通过向量检索 + BM25 完全可以做到。图数据库在"多跳关系查询"（如 A 起诉了 B，B 又起诉了 C，C 的律师是谁）时才显出优势——而你的案例库是裁判文书，每篇是独立的，不存在这种跨文档关联。

**什么时候值得做**
- 你明确需要"案例关系浏览"这个功能页面
- 并且当前搜索方式无法满足（比如"找被某某法院判过的、案由是交通肇事的、调解结案的案子"——这其实是结构化过滤，SQL 就够了，不需要图）

### 7. LLaMA-Factory SFT 微调

**它解决什么**
- 训练一个小模型专门做你的"意图分类"
- 替代 LLM prompt 方式，更稳定、更快、更便宜

**为什么现在不推荐**

| 成本项 | 评估 |
|--------|------|
| GPU 资源 | 本地 3060 可跑小模型（2B~7B），但训练时无法做其他事 |
| 标注数据 | 至少数百条分类标注（"这句话属于哪类意图"），纯手工活 |
| 运维成本 | 微调后的模型需要挂载到推理链路中，多一个部署单元 |
| 替代方案 | 基于 LLM prompt + few-shot 可以覆盖 80% 场景，零初始成本 |
| **收益** | 3% 的精度提升，还是在"意图分类"这个非核心路径上 |

**最关键的问题**：你的 TODO 是"用 LLaMA-Factory 真跑一次"——但跑完之后呢？小模型的分类精度一定不如大模型，部署维护还要额外成本。除非你的意图分类调用频率高到**每天成千上万次、用 LLM 成本不可接受**，否则 SFT 的投入产出比很低。

**什么时候值得做**
- 意图识别上线后，调用量达到规模化（日调用 > 1000 次）
- 且 LLM 方式的延迟/成本确实成为瓶颈
- 且你有充足标注数据（或能低成本生成）

## ✅ 值得做（独立评估）

### 5. MCP Server（半天）

**它解决什么**
- 把明镜的案件查询、法条检索、AI 问答包成标准的 MCP Tool
- 任何支持 MCP 协议的客户端（Claude Desktop、Cursor、VS Code 等）可以直接调用

**为什么值得**
1. **立即产出**：整个系统跑在你的 docker compose 里，不加新容器
2. **协议红利**：MCP 是 Anthropic 推动的标准，生态在快速膨胀，越早接入越便宜
3. **代码量少**：把现有的 FastAPI 接口包一层 MCP 适配器即可，不用重写业务逻辑
4. **具体收益**：你在 Claude Code 里就能直接查案子的数据、搜法条，不需要切浏览器

---

### 6. Ragas + LangSmith 评测（半天~1 天）

**它解决什么**
- 量化评估检索 + 回答质量，给出硬指标
- 回答"改完 BM25 到底有没有变好"——不再靠感觉

**为什么值得**
1. **现在的盲区**：你无法回答"BM25 混合后 recall 从多少涨到多少"——只能"感觉好像准了"
2. **优化迭代的靶子**：有评测指标后，每次改动都能测量效果变化，而不是"试试看"
3. **不是一次性**：评测集积累后，每次上线前跑一遍，防止回归
4. **LangSmith 免费额度够用**：日常开发量级不需要付费

## 一句话

| 方案 | 一句话 |
|------|--------|
| **MCP** | 半天包一层，生态红利，不做白不做 |
| **Ragas** | 给所有检索装尺子，不被感觉误导 |
| **Rerank** | RRF 不够好再加，但大概率够用了 |
| **LangGraph** | 等你遇到"单次搜不出来"的问题再动 |
| **Neo4j** | 除非你明确想要"关系图页面"，否则不做 |
| **SFT** | 调用量上千或有标注数据再说 |
